# Internationalization — Test Implementation

Scope: `src/i18n/**`, `src/types/app-config.d.ts` — locale resolution, message
catalogs, the React provider, and the server function that ships catalog data to
the client. The default locale is Arabic (`ar`), which means an unprefixed URL is
Arabic and English is always explicitly prefixed. Direction (`RTL`/`LTR`) is
derived from the locale, never from user input.

## Source map

| File                         | Responsibility                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------- |
| `src/i18n/i18n.config.ts`    | Supported locales, default locale and time zone, direction and OG-locale maps, locale guard helpers |
| `src/i18n/messages.ts`       | Catalog registry and `getMessages(locale)` lookup                                                   |
| `src/i18n/messages/en.json`  | English catalog: demo copy, metadata strings, 404 copy                                              |
| `src/i18n/messages/ar.json`  | Arabic catalog: same key tree, Arabic copy and plural forms                                         |
| `src/i18n/loadMessages.ts`   | `createServerFn` wrapper that validates a locale and returns its catalog                            |
| `src/i18n/i18n-provider.tsx` | `IntlProvider` wrapper that selects catalog and time zone                                           |
| `src/types/app-config.d.ts`  | Type augmentation tying `use-intl` to the supported locale and catalog shape                        |

## Test environment

- **Unit:** import the configuration module and catalogs directly. These are pure
  constants and lookups; no providers are required.
- **Component:** render children inside `I18nProvider` with Testing Library,
  under jsdom. Pass an explicit `timeZone` when the assertion depends on time
  zone so the test does not silently rely on the machine's zone.
- **Integration:** `loadMessages` is a `createServerFn` with a Zod validator.
  Exercise it through the TanStack Start server function runtime (or through a
  route that awaits it) rather than calling the handler object directly. Do not
  stub `createServerFn` itself; that would test the stub instead of the contract.
- **Auth/permissions:** not applicable. No auth middleware or permission guard is
  invoked in this area at this commit.
- **Determinism:** freeze the clock with `vi.useFakeTimers` and
  `vi.setSystemTime`. The demo date used by the UI is a module constant
  (`2026-01-01T00:00:00Z`), so tests must reuse that exact instant rather than
  "today". ICU output for Arabic differs across Node builds; when an assertion
  needs formatted text, compare against `Intl.DateTimeFormat` with the same
  locale and options, or pin the Node version in CI.
- **Money:** not applicable.

## Locale configuration

### I18N-001 · A supported locale string is returned unchanged

- **Covers:** `resolveLocale` — `src/i18n/i18n.config.ts`
- **Type:** unit · **Priority:** P1 · **Status:** Missing
- **Given** the supported locale list contains `ar` and `en`
- **When** `resolveLocale("en")` and `resolveLocale("ar")` are called
- **Then** each call returns the same value it received, with its narrow
  `Locale` type rather than a widened string
- **Notes:** include both locales; a test that only checks `en` would not prove
  the default locale can be selected explicitly.

### I18N-002 · Unknown or malformed locale input falls back to Arabic

- **Covers:** `resolveLocale` — `src/i18n/i18n.config.ts`
- **Type:** unit · **Priority:** P1 · **Status:** Missing
- **Given** the default locale is `ar`
- **When** the resolver receives `undefined`, the empty string, `"fr"`, `"EN"`,
  `"en-US"`, `"/en"`, or `"ar "` (trailing space)
- **Then** every call returns `"ar"` and never throws
- **Notes:** case-sensitivity and no trimming are part of current behavior. The
  route layer depends on this fallback, so it must be locked down before locale
  routing changes.

### I18N-003 · The locale guard accepts only exact supported tags

- **Covers:** `isLocale` — `src/i18n/i18n.config.ts`
- **Type:** unit · **Priority:** P0 · **Status:** Missing
- **Given** the guard is used by the `{-$locale}` route to reject bad prefixes
- **When** it is called with `"ar"`, `"en"`, `"EN"`, `"en-US"`, `"fr"`, `""`,
  `null`, `undefined`, a number, and an array containing `"ar"`
- **Then** it returns `true` only for the two exact strings `"ar"` and `"en"`
- **Notes:** this guard and `resolveLocale` intentionally disagree for `"fr"`
  (guard rejects, resolver falls back). Both behaviors are specified, and the
  route-level consequence is covered by `routes.md`.

### I18N-004 · Locale list, default locale, and default time zone are stable

- **Covers:** `locales`, `defaultLocale`, `defaultTimeZone` —
  `src/i18n/i18n.config.ts`
- **Type:** unit · **Priority:** P1 · **Status:** Missing

### I18N-011 · Arabic plural forms cover zero, one, and many

- **Covers:** `demo.items` — `src/i18n/messages/ar.json`
- **Type:** unit · **Priority:** P2 · **Status:** Missing
- **Given** the Arabic plural message with `=0`, `=1`, and `other` branches
- **When** it is formatted with counts `0`, `1`, and `3`
- **Then** the outputs are `لا توجد عناصر`, `عنصر واحد`, and `3 عناصر`
- **Notes:** Arabic has a dual category that the catalog does not define. The case
  covers only the branches that exist. The open question is recorded in the final
  report: should count `2` read `عنصران` rather than the generic `2 عناصر`?
  Answer it before adding dual support; do not change the case to hide it.

### I18N-014 · Dates default to the Riyadh time zone

- **Covers:** `I18nProvider` (`timeZone` default) —
  `src/i18n/i18n-provider.tsx`, `defaultTimeZone` — `src/i18n/i18n.config.ts`
- **Type:** component · **Priority:** P1 · **Status:** Missing
- **Given** a frozen instant of `2026-01-01T00:00:00Z`, which is 03:00 on the same
  day in Riyadh, and a provider with no `timeZone` prop
- **When** a child formats that instant with the `medium` date style
- **Then** the output represents 1 January 2026 in `Asia/Riyadh`
- **Notes:** this fixture does not distinguish Riyadh from UTC because both are
  on the same calendar day. A stronger fixture is an instant between 21:00 and
  23:59 UTC, which is the next day in Riyadh. Use one if the fixture can be
  changed without touching application code.
